## 2026-08-14｜YOLO 后肢依次抬高

- 原方案：最终抓取前先发送右后肢 `31=26°`，间隔 0.5 秒后再发送左后肢 `41=25°`。
- 停止原因：用户现场指出单侧先抬会使机身位置发生横移，破坏球与夹爪的对位。
- 证据：原抓球函数存在两条独立 `dog.motor` 命令及中间等待。
- 替代方案或后续动作：通过 `dog.motor([31, 41], [26, 25])` 在同一控制包中同步下发两侧后肢目标角度。

## 2026-08-14｜YOLO 仅在最终抓取前低趴

- 原方案：接近阶段保持默认行走站姿，达到抓取门槛后才低趴、抬高后肢和夹取。
- 停止原因：用户明确要求从一开始即低趴接近球，后肢只在最终夹取时抬高。
- 证据：用户现场纠正“ 一开始是按照低趴前进，到达为止之后再抬高后腿”。
- 替代方案或后续动作：步态只在启动时设置一次，随后下发低趴；接近脉冲不再重复切换步态，到位后才进入后肢抬高和夹取分支。

## 2026-08-14｜YOLO 接近阶段预先低趴

- 原方案：程序启动后立即设置低趴和后肢抬高，再开始转向、前进。
- 停止原因：用户要求接近阶段不切换低趴；而前进行走本身会恢复站姿，预先设置低趴不会保留到夹取时刻。
- 证据：程序前进时调用 `slow_trot`，用户现场观察到姿态恢复；代码路径显示低趴与最终夹取之间间隔多个行走脉冲。
- 替代方案或后续动作：接近阶段保持行走默认姿态；仅在检测达到抓取门槛后停止行走、低趴并重建机械臂准备姿态。

## 2026-08-14｜仅在 YOLO 程序开始时设置低趴

- 原方案：程序启动时设置低趴与后肢抬高，随后执行行走对准和前进，达到距离门槛后直接合爪。
- 停止原因：用户现场确认前进行走后车体已恢复站姿，球不在低趴抓取姿态对应的夹爪位置，无法夹到。
- 证据：代码在前进分支调用 `dog.gait_type("slow_trot")` 和 `dog.move_x`；该次流程日志已到达 `action=grab-complete`，但用户确认未夹到球。
- 替代方案或后续动作：在每次即将抓取时停止步态，重建低趴、后肢抬高和完整机械臂准备姿态，再闭爪。

## 2026-08-14｜YOLO 框半径回落与前进脉冲上限停止保护

- 原方案：YOLO 每次前进后要求检测框半径不低于上一步预期值，并在连续前进 6 个脉冲后强制退出。
- 停止原因：用户实机确认该策略在尚未夹到球时提前停止，不能完成抓球。
- 证据：2026-08-14 完整流程仅执行一次 `action=forward-step`，随后框半径由 25.2px 回落至 20.4px 即输出 `action=stop-no-approach`，未进入 `action=grab-start`。
- 替代方案或后续动作：不再用框尺寸的短时波动或前进次数中断流程；只要 YOLO 仍检测到球且框半径未达到抓取门槛，就继续按 0.08 秒脉冲接近。

## 2026-08-13｜固定绿色类别与 Picamera 通道二次交换

- 原方案：YOLO 抓球程序只读取 green 类（类别索引 2），并沿用 OpenCV BGR 摄像头路径的 `swapRB=True` 预处理。
- 停止原因：用户实机反馈识别结果不够准确；Picamera2 已输出 RGB888，再交换 R/B 会使模型输入颜色通道不符合训练输入。
- 证据：机器单帧日志表明模型可输出高置信度目标，但固定类别不满足“按模型目标”要求；代码检查确认 Picamera 配置为 RGB888。
- 替代方案或后续动作：按全部 YOLO 类别的最高置信度选择目标，并直接传入 RGB 图像；后续以真实球距离标定框尺寸到距离的映射。

## 2026-08-13｜YOLO 框尺寸直接套用厂商圆检测距离公式

- 原方案：把 YOLO 矩形框半径代入厂商 HSV/Hough 圆检测使用的 `54.82 - radius` 距离公式，以 13 cm 作为自动抓取阈值。
- 停止原因：实机出现持续前进直至目标退出视野，表明两种视觉特征的尺度不等价，距离阈值失真。
- 证据：运行日志持续输出 `dist≈35–41` 并重复 `action=forward-fast`，未进入抓取分支；用户现场确认机器不断前进直至球看不见。
- 替代方案或后续动作：直接以 YOLO 框半径做可标定抓取门槛（当前 28 px），前进改为受上限的 0.08 秒小步，并要求每步后框半径增加，否则停止。

## 2026-08-11｜按左前、右前、左后、右后解释轮控通道

- 原方案：将轮控数组顺序当作 `[左前, 右前, 左后, 右后]`，左转发送 `[-v, +v, -v, +v]`。
- 停止原因：实机观察到左前和右后同时向后转，说明负值落在物理对角线而非物理左侧。
- 证据：2026-08-11 左转实机命令 `[-0.35, +0.35, -0.35, +0.35]` 的轮向观察结果。
- 替代方案或后续动作：改按 `[左前, 右前, 右后, 左后]` 解释通道；左转发送 `[-v, +v, +v, -v]`，右转反向，并以短时实机验证。

## 2026-08-04｜保守 yaw 值 16 的临时标定方案

- 原方案：保持前后 XGO 值 8，仅将键盘 `a/d` 调整为受限 yaw 值 16。
- 停止原因：用户明确要求按机器随附的原厂 Dog_LM 控制逻辑实现；实机日志也证明问题不是按键链路，而是共享保守值下转向幅度不足。
- 证据：原厂 `dog_Joystick.py` 默认 `step_control=70`，前后映射约为 17、yaw 映射约为 55；XGO 库四足 yaw 范围为 100。
- 替代方案或后续动作：默认采用原厂前后 17、yaw 55 的强度，但继续保持键盘每次最长 0.20 秒、自动停止、急停和单次确认保护。

## 2026-08-02｜仅依赖初始源码导入扫描

- 原方案：导入时仅按文件名、配置字段和单行长凭据字面量筛选。
- 停止原因：预推送复核发现该规则遗漏了语音示例中的多行和非标准变量名凭据。
- 证据：12 份导入文件含硬编码云服务令牌或应用标识。
- 替代方案或后续动作：在提交前执行覆盖多行赋值、令牌和服务商常见命名的独立扫描，并删除命中文件后重建校验清单。

## 2026-08-17｜刷机 Ubuntu 22.04 原生跑 ROS1（评估否决）

- 原方案：质疑 Docker 容器运行形态，改为把 CM5 从厂商预装系统刷成 Ubuntu 22.04，原生安装 ROS1 Noetic 跑导航栈。
- 停止原因：官方支持矩阵三重互斥——① Ubuntu 22.04 官方树莓派镜像仅适配 Pi 2/3/4，不含 BCM2712 DTB，不支持 CM5（CM5 需 24.04 LTS 起）；② ROS1 Noetic 官方二进制仅支持 Ubuntu 20.04（REP 3），而 20.04 同样不支持 CM5 → **不存在任一版 Ubuntu 同时原生支持 CM5 + Noetic**；③ 更硬的是厂商相机栈 picamera2/libcamera 在 Ubuntu 25.04 之前不可用（LP: #2038669），即使刷 24.04 相机也起不来。
- 证据：Canonical 官方硬件支持矩阵（Pi 5/CM5 在 22.04 列为空）、23.10 发布说明（首次支持 Pi 5、实验性）、24.04 发布说明（首个支持 Pi 5 的 LTS）、REP 3（Noetic 仅 Focal）、wiki.ros.org noetic 安装页（仅 20.04 仓库）。详见 2026-08-17 librarian 查证记录。
- 替代方案或后续动作：维持 Docker 容器跑 ROS1 Noetic 的现状，补齐实机欠账——容器补 `/dev/ttyAMA0` 串口直通（2026-08-16 发现缺失），按 `docs/technical/2026-08-16-docker-runtime-unification.md` §2.1/§2.3 重建或 docker update 容器并验证。当前实机问题属设备直通配置缺失，非架构选型错误。

## 2026-08-02｜通用 Docker Hub 代理拉取 ROS 镜像

- 原方案：先在 Docker 的 `registry-mirrors` 中配置 DaoCloud 并按标准标签拉取；随后使用 DaoCloud、Aityp 和 1ms 的公开代理路径拉取官方 ROS 摘要。
- 停止原因：三个通用代理均无法持续传输 ROS Noetic 的历史大镜像层；Aityp 另对指定路径要求认证。
- 证据：Docker 日志连续出现 `Host doesn't match`，各次拉取在数分钟内仅完成极小层；Aityp 返回 `authorization failed: no basic auth credentials`；`/var/lib/docker` 保持约 656 KiB。
- 替代方案或后续动作：使用华为云公开的、已预同步该镜像 ARM64 变体的专用路径，拉取后按公开的镜像 ID、架构与 ROS 发行版验证。
