# 2026-08-16 犯错记录

### Codex 工作区命令 CreateProcessAsUserW 错误 5

- **现象**：Codex 在工作区启动 PowerShell 命令时返回 `CreateProcessAsUserW failed: 5 (拒绝访问)`，无法读取文件或执行 Git。
- **原因**：当时任务的终端执行环境未获得工作区进程创建权限；仓库和 Git 远端连接本身没有异常。
- **修复**：恢复允许创建工作区进程的执行环境后，重新读取项目记录、获取远端并以快进方式更新本地分支。
- **预防**：遇到错误 5 时先确认 Codex 任务的终端/权限环境，再重试命令；不要将该错误误判为 Git、远端凭据或仓库文件权限故障。

## ssh 远程一键命令里 pkill -f 匹配到远程 shell 自身命令行，命令中断无输出（复现 2026-08-08 同类）

- **现象**：`ssh pi@… "pkill -f follow_line.py; sleep 2; pgrep…; …"` 整条命令无任何输出返回（连分隔符 echo 都没有），恢复服务等后续命令全没执行。
- **原因**：ssh 把整条命令交给远程 `bash -c` 执行，远程 shell 自身命令行包含 "follow_line.py" 字样；`pkill -f` 按全命令行模式匹配，把远程 bash 自己也杀了 → 后续命令不执行、ssh 空返回。（2026-08-08 已记"pkill -f 会匹配到 SSH 会话自身的命令行"，本次复现。）
- **修复**：改分步：先 `pgrep -af follow_line.py` 列出 PID，再 `kill <pid>` 定点杀；确认 python 进程已死后直接继续恢复服务。
- **预防**：远程 ssh 一键命令里避免 `pkill -f <关键字>`；必须用时把 pkill 放最后一条、或先用 pgrep 拿 PID 再 kill、或让模式不命中 bash -c（如 `pkill -f 'xgovenv/bin/python.*follow_line'`）；杀进程与后续动作分两条 ssh 命令。

## 测试脚本修改 XGO 固件模式（enable_wheel_control）后未恢复，导致后续 move_x 全部失效

- **现象**：锁轮测试（enable_wheel_control(1) + wheel_control 128）后直接跑主流程/抓球程序，狗原地转圈（YOLO 引导的 turn 正常）但 move_x 前进完全无效，抓球接近（move_x(3)）也失效。
- **原因**：`enable_wheel_control(1)` 把狗切到 wheel 模式，测试脚本结束时未恢复（未调 `enable_wheel_control(0)`）；wheel 模式下 move_x 步态命令失效（只有转向 turn 仍响应），且 wheel_control 单发/10Hz 刷新均不驱动轮子（固件不可用）。
- **修复**：`enable_wheel_control(0)` 恢复默认腿模式（`restore_mode.py` 已写好，机器来电后执行），move_x 恢复。
- **预防**：任何修改 XGO 固件状态（wheel flag、姿态、步态）的测试脚本，结束前必须显式恢复默认状态；排查"突然不能前进只能转"先怀疑固件模式残留，检查测试脚本最后改了什么。另：wheel_control 的输入是 0-255 字节编码（128=停、>128 前进、<128 后退，wheel_byte 公式），不是直接速度值。

## CRLF 污染 scp 部署的 Python 脚本：shebang `python3\r` 使 roslaunch 启动失败（复现 2026-08-15 同类）

- **现象**：roslaunch 里 simple_odom 节点启动即死（`process has died ... exit code 127`），无节点日志；rosnode list 缺 simple_odom → odom→base_link TF 缺 → AMCL 无运动预测不发 map TF → move_base 全程报 `Timed out waiting for transform from base_link to map`；而手动 `python3 simple_odom.py` 运行完全正常。
- **原因**：Windows 端生成/编辑的 `simple_odom.py`（新增 odom_scale 参数后 scp 覆盖部署）带 CRLF 行尾，shebang 变 `#!/usr/bin/env python3\r`；roslaunch 直接执行脚本（走 shebang）→ `/usr/bin/env: 'python3\r': No such file or directory` → exit 127。手动显式 `python3 xxx.py` 调用**绕过 shebang**，不报错，掩盖了问题——两次"手动跑正常"直接把排查引向 roslaunch 环境/进程管理，浪费大量时间。
- **修复**：容器内 `sed -i 's/\r$//'` 转 LF（simple_odom.py、main_flow.py）→ 重启 launch → simple_odom 正常注册、TF/AMCL/move_base 全链路恢复。
- **预防**：① roslaunch 直接执行的脚本（`type=*.py` 走 shebang）部署后必须验证 shebang 无 `\r`（`head -1 | xxd` 或容器 `bash -x` 试跑）；② "手动 python3 显式调用正常"不能证明部署 OK，必须按 roslaunch 的执行方式（shebang）验证；③ 排查 roslaunch 节点死亡先看 launch 日志的 `process has died ... exit code 127` 行，`python3\r` 是 CRLF 的指纹；④ 本次教训与 2026-08-15「CRLF 污染仓库 shell/Python 脚本」同源：Windows 端编辑的脚本在上传/部署前统一做行尾检查。
