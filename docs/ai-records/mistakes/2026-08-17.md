# 2026-08-17 犯错记录

### simple_odom yaw_jump_limit=0.4 丢弃真实转向导致 odom 漂移

- **现象**：主流程实机跑，waypoint 5 局部规划器 7 秒 ABORTED；机器静止时
  odom→base (4.88,2.49) yaw 134°，实际 (2.03,-0.19) yaw≈101°；日志
  `imu yaw jump 0.43 rad dropped`。
- **原因**：`simple_odom.py` 的 IMU 跳变过滤阈值 0.4 rad/帧（10Hz）按"平滑连续
  转向"设计（0.6 rad/s × 0.1s = 0.06 rad/帧），但 XGO 的转向是**脉冲式**
  （cmd_vel 桥把 wz 映射为 turn 步长突发），单帧 IMU 变化轻松超过 0.4 rad。
  超限被当跳变丢弃且 `_last_raw = raw` 把该段真实转向永久抹掉 → odom 朝向
  系统性落后 → `dx = vx*cos(heading)*dt` 平移积分方向错误 → odom 路径与实际
  分叉漂移。AMCL 运动模型吃 odom 增量，粒子传播同样被污染。
- **修复**：yaw_jump_limit 默认 0.4 → 1.5（只滤 ±π 环绕之外的真正异常，±π
  环绕已单独处理）；更根本的是 AMCL 模式改用 odom_from_amcl（AMCL 位姿回灌，
  foot 步态无编码器时 cmd_vel 积分 odom 本质不可信，见 CHANGE_LOG 2026-08-17
  "实机导航改造"条目）。
- **预防**：IMU/传感器跳变过滤阈值必须结合执行器的真实运动特性（连续型还是
  脉冲型）设定；里程计数据上线前做静止与运动两种场景的数值核对。

### TF 发布者与消费者互相等待死锁（odom ↔ AMCL）

- **现象**：launch 重启后 AMCL 报 "No laser scan received"，/amcl_pose 永不
  发布，rosout 显示 AMCL 订阅列表里无 scan 处理记录。
- **原因**：odom_from_amcl 首帧前不发布任何 TF（等 /amcl_pose），而 AMCL 的
  laser 处理挂在 tf::MessageFilter 上等 laser→odom 的 TF（odom_from_amcl 发布）
  → 两个节点互相等待，死锁。
- **修复**：odom_from_amcl 加 init_x/init_y/init_yaw 参数，首帧 amcl_pose 到来
  前用初始位姿无条件发布 odom→base TF。
- **预防**：TF 发布者必须在收到任何依赖数据前发布默认/初始 TF；凡是
  "A 节点输出依赖 B 节点、B 又消费 A 的 TF"的链要检查启动时序环。

### foot 步态机器人用 cmd_vel 积分 odom 不可信（架构级）

- **现象**：odom_scale=0.23 标定后 1m goal 实测 85~146cm 随机波动；odom 方向
  漂移（见上一条）；主流程 waypoint 反复失败。
- **原因**：XGO mini3W 是轮足（foot 步态），轮子自由滚动+打滑，无编码器；
  cmd_vel 积分与实际位移无稳定映射（打滑 ±20% + 桥非线性映射 + 步态随机性），
  任何标定系数都只是近似。用户判定：比赛场景激光始终可用、无激光退化场景，
  定位应全权交给 AMCL（激光匹配），不需要 odom。
- **修复**：AMCL 模式停用 cmd_vel 积分 odom，新增 odom_from_amcl（AMCL 位姿
  EMA 平滑回灌 odom，map→odom 自动趋于恒等）。
- **预防**：选择里程计方案前先确认底盘执行器类型（轮式编码器/步态/打滑特性）；
  无编码器且激光可靠时优先激光定位回灌，不要硬调积分标定系数。

### Docker update 不支持 --device-add，设备变更必须重建容器

- **现象**：`docker update --device-add=/dev/ttyAMA0:/dev/ttyAMA0 ros-noetic`
  报 `unknown flag: --device-add`（Docker 29.7.1）。
- **原因**：docker update 只支持资源限制类配置（cpu/memory/restart 等），
  设备映射与挂载不在其列。
- **修复**：rename 旧容器兜底 → docker run 重建（补齐 --device/-v）→ 验证后
  再处理旧容器。
- **预防**：容器设备/挂载需求变化时直接走重建流程（记录完整 run 参数），不要
  指望 docker update。

### 容器重建丢失容器内 apt 安装的包

- **现象**：导航容器重建后 catkin_make 失败——ricam_dataset_capture 缺
  cv_bridge。
- **原因**：旧容器里 apt 装过 ros-noetic-cv-bridge（及其 GUI 依赖链），这些
  增量安装只存在于旧容器可写层；从镜像重建的新容器只有镜像层内容。
- **修复**：新容器 apt install ros-noetic-cv-bridge 后 catkin_make 通过。
- **预防**：容器重建后按依赖清单重装；关键 apt 增量应固化进镜像或安装脚本
  （可对比旧容器的 dpkg 列表 diff 找差异）。

### libcamera 在容器内枚举相机依赖 udevd（/run/udev/data）

- **现象**：bookworm 球容器内 picamera2 初始化报 IndexError（global_camera_info
  空），DEBUG 日志连枚举器输出都没有；宿主同样代码枚举正常。
- **原因**：libcamera 的 udev 枚举器读设备 udev 属性（依赖计数）依赖 udevd
  生成的 /run/udev/data 数据库；容器内无 udevd（也试过 libudev1、--privileged、
  全 /dev 挂载均无效），枚举静默为空。
- **修复**：容器内 apt install udev + `/lib/systemd/systemd-udevd --daemon` +
  `udevadm trigger`，之后成功枚举 rp1-cfe/pispbe 并实拍 (480,640,3)。
- **预防**：容器内跑 libcamera/Picamera2 必须带 udevd；排查"静默空枚举"时优先
  检查 /run/udev/data 是否存在。

### rpi-lgpio 硬件检测在容器内失败，用 RPI_LGPIO_REVISION 绕过

- **现象**：容器内 `import RPi.GPIO`（rpi-lgpio 0.6）报 "This module can only
  be run on a Raspberry Pi"，读 /proc/device-tree/system/linux,revision 失败。
- **原因**：rpi-lgpio 检测链：环境变量 RPI_LGPIO_REVISION → device-tree 文件
  → 报错；容器内 /proc/device-tree 挂载不全。
- **修复**：设置环境变量 `RPI_LGPIO_REVISION=00c041a0`（宿主
  /proc/device-tree/system/linux,revision 的 hex 值），检测直接通过。
- **预防**：容器内跑树莓派硬件库（RPi.GPIO/rpi-lgpio）时优先用官方支持的环境
  变量注入机制，不要硬改库。

### 厂商 venv 是 system-site-packages 且 editable install 不入 .pth

- **现象**：球容器 ballenv 通过 extra.pth 兜底宿主 xgovenv site-packages 后
  `import uiutils` 仍报 ModuleNotFoundError。
- **原因**：uiutils 在宿主 xgovenv 是 editable install（`__editable__.uiutils-1.0.0.pth`
  的 import hook），其源目录在 site-packages 之外；Python 的 site 模块只处理
  site-packages 目录本身的 .pth，通过 extra.pth 加入的**其他目录**里的
  .pth/egg-link 不会被处理。另外 xgovenv 是 `--system-site-packages` venv，
  numpy/picamera2 等在宿主系统 dist-packages 而非 venv 内。
- **修复**：extra.pth 直接加 uiutils 源码路径 `/home/pi/RaspberryPi-CM5/uiutils/src`。
- **预防**：复用外部 venv 前先确认包安装形态（普通/editable/system-site-packages），
  editable 包要直接指向 src 路径。

### pkill -f roslaunch 匹配 docker exec 自身命令行（复现）

- **现象**：`docker exec ros-noetic bash -lc "pkill -f roslaunch ..."` 命令
  中断无输出，后续 echo 未执行。
- **原因**：pkill -f 匹配完整命令行，docker exec 的 bash -lc 参数里含
  "roslaunch" 字样，把自己也杀了（2026-08-08/16 同类复现）。
- **修复**：改用 `pkill -f "[r]oslaunch"` 技巧或先 pgrep 拿 PID 再 kill。
- **预防**：见 2026-08-08 条目；远程一键命令里 pkill -f 必须用字符类技巧。

### xgolib read_imu() 的 0x65 批量读在此固件（M-7.0.0b8）上返回固件版本串

- **现象**：扩展 manual_control_server 的 /imu 用 read_imu()（0x65 读 24 字节）
  返回 accel/gyro/euler，实测数据物理不合理：|g|=15.65、gyro.x 恒定 1532 dps、
  euler 全 0，且 5 次采样完全不变。
- **原因**：原始 24 字节 hex 是 ASCII 固件版本串（"0.0b8"）——**0x65 在
  M-7.0.0b8 固件上是"读固件版本"协议，不是 IMU 批量读**；xgolib 1.0.3 的
  unpack_imu 把版本串当 int16/float 解析出垃圾。单轴读 0x66/0x67/0x68
  （read_roll/read_pitch/read_yaw）有效：yaw 是**累积角**（多圈，实测 -3847°），
  pitch/roll 是体角（度）。固件无原始 accel/gyro 流。
- **修复**：/imu 端点回退为 0x66/67/68 三连读（read_imu_angles），新增 euler
  (rad) 字段；imu_bridge 的 angular_velocity.z 用 yaw 差分计算，
  linear_acceleration 置零（无数据）；Cartographer 降级 use_imu_data=false
  （纯激光 2D SLAM，官方支持）。
- **预防**：用厂商 SDK 的批量传感器接口前必须抓原始帧 hex 验证协议与固件版本
  匹配（不同型号/固件 0x65 语义可能完全不同）；"数值稳定但物理不合理"是解析
  错位（读到别的地址/字段）的典型信号。

### ROS Noetic 官方 apt 仓库没有 arm64 的 cartographer 预编译包

- **现象**：`apt-get install ros-noetic-cartographer-ros` 报
  `E: Unable to locate package`；snapshots.ros.org/noetic/final 与
  packages.ros.org/ros/ubuntu 两个源都搜不到。
- **原因**：ROS Noetic 官方二进制只覆盖 arm64 的部分包集合——arm64 仓库
  （binary-arm64，3668 包）里没有 cartographer/cartographer_ros（重依赖
  ceres/absl，官方未为 arm64 构建）。focal 源里也没有 libabsl-dev
  （absl 仅在较新发行版有包）。
- **修复**：本机（Windows）从 GitHub 下载 cartographer/cartographer_ros
  1.0.0 tag 源码 zip → scp 真机 → docker cp 容器 → 源码编译（1.0.0 不依赖
  absl，依赖 ceres/protobuf/lua5.3/glog/gflags/boost，focal 源均有）。
- **预防**：arm64 + Noetic 环境先用 `curl binary-arm64/Packages.gz` 验证包存在
  再决定 apt 还是源码编译；容器内 GitHub 不通时从本机下载源码再 scp。

### 脚本改版后未重新部署真机/容器，实机跑旧版（imu_bridge fetch failed: 'accel'）

- **现象**：carto 模式启动后 /imu 话题无消息，日志
  `imu_bridge fetch failed: 'accel'`（KeyError）；容器 devel 空间仍是 9 轴版
  imu_bridge（读 accel/gyro 字段），而服务端已按固件限制回退姿态角版。
- **原因**：第一版 imu_bridge.py（9 轴）部署并编译进容器后，因 0x65 协议不可用
  重写为姿态角版，但只重新部署了 manual_control_server.py，**漏部署/漏编译
  imu_bridge.py**——容器里跑的是旧版。
- **修复**：重新 scp imu_bridge.py → docker cp → catkin_make 后 /imu 30Hz 正常。
- **预防**：源码改版后必须"改 → 部署 → 容器编译"三步都执行并验证节点日志；
  实机报数据字段类错误（KeyError/字段缺失）时优先怀疑两端版本不同步（对比
  真机文件与容器内文件哈希）。

### cartographer_node 1.0.0 用 gflags 命令行参数，不读 ROS param

- **现象**：carto 模式启动后 cartographer_node 立即崩溃（Check failure:
  `-configuration_directory is missing`），launch 里 <param> 已设置但无效。
- **原因**：cartographer_node 的 main 用 `google::ParseCommandLineFlags` 读
  gflags（单/双横线参数），不会读 ROS param server；launch 的 <param> 只进
  param server 不被消费。
- **修复**：launch 的 <node> 加 `args="-configuration_directory $(find ...)/config
  -configuration_basename xxx.lua"`（roslaunch 会把 args 拼进节点 argv）。
- **预防**：第三方节点若崩在启动即 CHECK gflags/命令行参数，先看其 main 是否
  ParseCommandLineFlags；<param> 与 <node args> 两种传参方式要按节点实现选择。
