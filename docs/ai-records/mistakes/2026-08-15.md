# 2026-08-15 犯错记录

## lidar_loc 激光扫描点 y 坐标取负导致定位 180° 镜像

- **现象**：定点导航时目标在前方，机器人却原地掉头 180° 后朝反方向直行；RViz 中地图/点云看起来镜像错位。
- **原因**：`jie_ware/lidar_loc.cpp` 扫描点转换写死 `y_laser = -r*sin(angle)`，与 ROS LaserScan 标准约定（逆时针为正、`+sin`）相反，点云左右镜像；贪心匹配（±1°±1px 局部搜索、收敛判据只看 10 帧稳定不看匹配质量）把镜像点云对到镜像位姿并锁死，`map→base_link` 朝向错 180°，局部规划器据此掉头。
- **预防**：同一份 `/scan` 被多个节点消费时，逐节点核对极坐标→直角坐标转换符号；可对照"标准转换节点点云显示正确"来定位镜像源；镜像 bug 只污染定位 TF，不污染地图（无需重新建图）。

## launch env 硬编码 local_master_ip 覆盖命令行 export

- **现象**：实机容器节点注册报 `No route to host`，节点日志显示连的是 `http://192.168.137.232:11311`（旧 WSL IP），尽管命令行已 `export ROS_MASTER_URI=http://192.168.137.193:11311`。
- **原因**：`robot_dog_main.launch` 用 `<env name="ROS_MASTER_URI" value="http://$(arg local_master_ip):11311"/>` 强制覆盖环境变量，`local_master_ip` 默认值 232 已过时（WSL IP 由 DHCP 每次变化，当前 193）。
- **修复**：启动时传参 `local_master_ip:=192.168.137.193`。
- **预防**：实机 launch 必须带 `local_master_ip:=<当前WSL IP>`；排查"节点连错 master"先看 launch 文件的 `<env>`/`<arg>` 覆盖，再怀疑网络。另：roslaunch 连不上 master 时会 auto-start 本地 rosmaster 兜底（节点 env 仍指向原 URI），容器内出现 rosmaster 进程不要误判为配置错误。

## scp/docker cp 覆盖部署丢可执行权限

- **现象**：`roslaunch ... Cannot locate node of type [simple_odom.py] in package [robot_dog_navigation]. Make sure file exists ... permission is set to executable (chmod +x)`，节点完全没启动。
- **原因**：scp + docker cp 覆盖文件后权限重置为 644，roslaunch 要求脚本可执行。
- **修复**：容器内 `chmod +x`。
- **预防**：向实机容器部署脚本类节点后必须 `chmod +x` 并 `python3 -m py_compile` 验证，再重启 launch。

## WSL 后台进程随 wsl.exe 返回被清理

- **现象**：`wsl -- bash -c "nohup roscore ... &"` 返回后数秒，roscore/roslaunch/rviz 全部消失，master 不可达。
- **原因**：WSL2 在客户端断开后清理进程树，nohup 不顶用（SIGTERM 不挡）。
- **修复**：用 `Start-Process wsl.exe -WindowStyle Hidden` 跑前台守护脚本（内部起子进程后 `wait` 阻塞），wsl.exe 常驻使 WSL 实例存活。
- **预防**：WSL 长驻服务（roscore/rviz）一律用守护脚本 + Start-Process 方式启动；不要用 `wsl -- bash -c "... &"` 内联后台。

## CRLF 污染仓库 shell/Python 脚本（复现 2026-08-03 同类）

- **现象**：`bash wsl-simulation/start_local_control.sh` 报 `$'\r': command not found`、`set: - : invalid option`；ball_spotter 节点报 `/usr/bin/env: 'python3\r': No such file or directory`。
- **原因**：仓库内 wsl-simulation/*.sh 与 ball_spotter 的 .py/.launch 全部是 CRLF 行尾（Windows 端保存所致）。
- **修复**：WSL 内 `sed -i 's/\r$//'` 批量转 LF。
- **预防**：Windows 端编辑 WSL/实机执行的脚本后，执行前先 `file` 检查行尾；本次已把 wsl-simulation 全部脚本与 ball_spotter 源文件转成 LF。

## simple_odom 用 IMU 绝对 yaw 当基准导致机器朝向斜

- **现象**：建图模式 rviz 里机器斜了约 26°（IMU yaw=25.67°），不朝地图 +X。
- **原因**：`simple_odom.py` 的 `_accum_yaw` 首帧基准取 IMU 绝对磁力计朝向，`init_yaw` 参数被每帧 IMU heading 无条件覆盖，形同虚设。
- **修复**：首帧基准改为 `self._accum_yaw = self.init_yaw`（0），之后仍跟随 IMU 相对变化。验证 tf_echo odom base_link RPY=[0,0,0]。
- **预防**：涉及起点的坐标基准必须用相对量或显式 init 参数，不能用传感器绝对读数直接当基准。

## 实机建图未扫全：右下角未知区导致 navfn 规划失败

- **现象**：主流程 waypoint 3/4（场地右下方）move_base 秒级 ABORTED（"Failed to get a plan"），目标点在静态地图上看起来 free。
- **原因**：`ricam_arena_mapped`（8-15 03:42 建图）右下角（y≤-1.2）从未被扫描 = 未知区；navfn 未设 `use_unknown_as_free` 时把 unknown 当 lethal，目标点落入未知区 → 全局规划无解。另外全局 costmap 中 y=-0.85~-1.1 存在实时激光障碍的膨胀高代价带（cost 99-100，静态地图此处是 free），进一步压缩右侧可行域。
- **修复**：主流程 `--side-distances` 缩到已知区（0.5,0.25,-0.575，y≥-0.75）；最终路径需补建图扫右下角后恢复 0.5,1.65,-0.575。
- **预防**：排查 "Failed to get a plan" 顺序：① 订阅 `/map` 查目标点及邻域占用（-1=未知区是首要嫌疑）；② 订阅 `/move_base/global_costmap/costmap` 查合并值（区分静态地图与实时障碍膨胀）；③ 确认 navfn `use_unknown_as_free` 参数。建图完成后应抽查场地四角是否扫全（回放 `map_saver` 结果看四角有无 -1），避免导航阶段才发现。

## cmd_vel 桥 x 步长死区 + yaw 优先分支导致实机"只转不走"

- **现象**：主流程实机首跑，move_base 输出正常（cmd_vel vx 最高 0.79 m/s）、单点测试 5.4s 即 SUCCEEDED，但狗原地不动、只能左右转；waypoint 1/2 被"到达"（odom/AMCL 假前进）而 waypoint 3 规划失败 ABORTED；手控服务日志 POST 计数对比 delta=0。
- **原因**：两个因素叠加。
  1. 桥 x 映射 `x_scale_ref=4.0`：move_base 典型 vx 0.1~0.8 m/s 经 `_scale_step` 只映射到步长 12.1~13.0，正好压在 XGO 固件运动死区（~12，实测 13 仍几乎不动）边缘，狗基本不走；而 yaw 步长 17~27 明显能转，表现就是"只能左右转"。
  2. 桥 `_control_tick` 的 yaw 优先分支（`|wz|>dead_zone_wz(0.05)` 就发 yaw 并 elif 掉 x）：move_base 弧线/转向段 vx 与 wz 同时非零时 x 永远被吃掉。单点测试 cmd_vel 全部样本 `wz>0.05`，桥一次 x 脉冲都没发（节点日志可见）。
  3. 排查干扰：手控服务 systemd 07:05 重启后日志不再写入旧文件 `manual_control.log`（mtime 停在 06:24），POST 计数对比 delta=0 是假象；桥的真实日志在容器 `/root/.ros/log/<run>/oumax_cmd_vel_bridge-*.log`（roslaunch 节点专属日志），不是 launch stdout 重定向文件。
- **修复**：`robot_dog_main.launch` 桥参数 `x_scale_ref 4.0→0.2`（0.2 m/s 即满步长）、新增 `linear_motion_value 25`、`x_min_step 12→15`、`dead_zone_wz 0.05→0.10`（小角度偏差容忍、直线段优先发 x）。已同步仓库与部署版，待重启 launch 后单点复测。
- **预防**：实机桥类速度映射必须实测各轴实际步长与固件死区，不能只按注释值推断；排查"只转不走"先看桥节点 `/root/.ros/log` 的 `OUMAX pulse` 记录，区分"没发命令"与"发了命令狗不动"；systemd 服务的日志位置变化（旧文件遗留 vs journald）会导致文件级统计失真，对比前先确认服务进程实际写哪。
